## 1. Conventional Commits — Quy Chuẩn Đặt Tên Thông Điệp Commit

Conventional Commits cung cấp một cấu trúc ngữ nghĩa có thể phân tích tự động bằng máy (Machine-readable), giúp tự động hóa việc tính toán phiên bản phần mềm theo **Semantic Versioning (SemVer)** và tự động sinh Changelog / Release Notes.

### 1.1. Cấu Trúc Thông Điệp Chuẩn
```text
<type>[optional scope]: <description>

[optional body]

[optional footer(s)]
```

### 1.2. Danh Mục Các Loại (Types) Chuẩn & Tác Động Phiên Bản SemVer
| Loại Type | Ý nghĩa & Khi nào dùng | Tác động SemVer |
|---|---|---|
| **`feat`** | Thêm một tính năng mới cho người dùng | Tăng **MINOR** (`v1.2.0` $\rightarrow$ `v1.3.0`) |
| **`fix`** | Sửa một lỗi / bug trong mã nguồn | Tăng **PATCH** (`v1.2.0` $\rightarrow$ `v1.2.1`) |
| **`perf`** | Cải thiện hiệu năng xử lý (bộ nhớ, tốc độ query) | Tăng **PATCH** |
| **`refactor`** | Tái cấu trúc mã nguồn (không đổi tính năng, không sửa bug) | Không đổi version (nội bộ) |
| **`test`** | Bổ sung hoặc sửa các bài kiểm thử | Không đổi version |
| **`docs`** | Chỉ thay đổi tài liệu (README, Markdown) | Không đổi version |
| **`build`** | Thay đổi hệ thống build hoặc dependency (pom.xml, package.json) | Không đổi version |
| **`ci`** | Thay đổi cấu hình CI/CD (GitHub Actions, GitLab CI) | Không đổi version |
| **`chore`** | Các công việc dọn dẹp phụ trợ khác | Không đổi version |

### 1.3. Khai Báo Thay Đổi Phá Vỡ Tương Thích (Breaking Changes)
Thêm dấu chấm than `!` ngay sau Type/Scope hoặc thêm dòng `BREAKING CHANGE:` ở phần Footer để kích hoạt tăng **MAJOR** (`v1.0.0` $\rightarrow$ `v2.0.0`):
```text
feat(orders)!: thay doi cau truc tra ve cua API tao don hang

BREAKING CHANGE: Truong 'order_id' duoc doi ten thanh 'orderCode' theo chuan moi.
```

> [!IMPORTANT]
> **Quy tắc cứng gdt-workspace:** Thông điệp commit chỉ mô tả thay đổi kỹ thuật. Tuyệt đối không ghi "Generated by AI", không ghi tên mô hình LLM, không thêm dòng Co-Authored-By AI.

## 2. OpenAPI 3.0 (Swagger) — Đặc Tả Hợp Đồng REST API Chuẩn

OpenAPI 3.0 là chuẩn công nghiệp để mô tả giao diện lập trình ứng dụng RESTful. Tiếp cận **Contract-First (Đặc tả trước khi code)** giúp Frontend và Backend có thể phát triển song song thông qua Mock Server.

### 2.1. Bản Mẫu OpenAPI 3.0 Hoàn Chỉnh (YAML)

```yaml
openapi: 3.0.3
info:
  title: Accounting & Order API
  version: 1.2.0
  description: Hệ thống API quản lý đơn hàng và tích hợp bưu cục J&T
servers:
  - url: https://api.gdttech.net/api/v1
    description: Production Server

paths:
  /orders:
    post:
      summary: Tạo mới đơn hàng
      operationId: createOrder
      tags:
        - Orders
      security:
        - BearerAuth: []
      requestBody:
        required: true
        content:
          application/json:
            schema:
              $ref: '#/components/schemas/CreateOrderRequest'
      responses:
        '201':
          description: Đơn hàng đã được tạo thành công
          content:
            application/json:
              schema:
                $ref: '#/components/schemas/OrderResponse'
        '400':
          description: Dữ liệu đầu vào không hợp lệ

components:
  securitySchemes:
    BearerAuth:
      type: http
      scheme: bearer
      bearerFormat: JWT

  schemas:
    CreateOrderRequest:
      type: object
      required:
        - customerId
        - items
      properties:
        customerId:
          type: integer
          format: int64
          example: 10023
        items:
          type: array
          minItems: 1
          items:
            $ref: '#/components/schemas/OrderItemRequest'

    OrderItemRequest:
      type: object
      required:
        - productId
        - quantity
      properties:
        productId:
          type: integer
          format: int64
        quantity:
          type: integer
          minimum: 1
          example: 2

    OrderResponse:
      type: object
      properties:
        orderCode:
          type: string
          example: "ORD-20261028-A98B"
        status:
          type: string
          enum: [DRAFT, CONFIRMED, SHIPPING, DELIVERED, CANCELLED]
        totalAmount:
          type: number
          format: double
          example: 350000.00
```

## 3. Spotify Backstage — Cổng Thông Tin Kỹ Sư & Software Catalog

Backstage (sáng tạo bởi Spotify, hiện thuộc CNCF) giải quyết vấn đề phân mảnh phần mềm trong doanh nghiệp bằng cách định nghĩa **Sổ Cái Thành Phần Phần Mềm (Software Catalog)** ngay bên trong mã nguồn thông qua file `catalog-info.yaml`.

### 3.1. Cấu Trúc Khai Báo `catalog-info.yaml` Chuẩn

Đặt file này tại thư mục gốc của mỗi service (ví dụ: `business/accounting-service/catalog-info.yaml`):

```yaml
apiVersion: backstage.io/v1alpha1
kind: Component
metadata:
  name: accounting-service
  title: Accounting & Order Management Service
  description: Service xử lý nghiệp vụ đơn hàng, kho bãi, CSKH và đối soát bưu cục
  annotations:
    github.com/project-slug: gdt-workspace/accounting-service
    backstage.io/techdocs-ref: dir:.
    prometheus.io/rule: api_http_requests_total
  tags:
    - java
    - spring-boot
    - microservice
    - order-fulfillment
spec:
  type: service
  lifecycle: production
  owner: group:backend-team
  system: gdt-platform
  providesApis:
    - order-api
  consumesApis:
    - iam-auth-api
    - jnt-express-api
  dependsOn:
    - resource:postgresql-cluster
    - resource:redis-cache
    - resource:rabbitmq-broker

---
apiVersion: backstage.io/v1alpha1
kind: API
metadata:
  name: order-api
  description: REST API xử lý vòng đời đơn hàng
spec:
  type: openapi
  lifecycle: production
  owner: group:backend-team
  system: gdt-platform
  definition:
    $text: ./docs/openapi/orders-v1.yaml
```

**Lợi ích đột phá:**
- Nhìn thấy toàn bộ sơ đồ phụ thuộc (Dependencies Graph) giữa các service.
- Biết chính xác đội ngũ nào sở hữu (`owner: group:backend-team`), trạng thái vòng đời (`production`).
- Tự động biên dịch tài liệu TechDocs từ Markdown thành trang tra cứu nội bộ đẹp mắt.
